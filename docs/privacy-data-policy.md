# 개인정보 처리 정책

해피간병 전자간병일지 시스템이 수집·저장하는 개인정보와 그 처리 원칙을
정리한다. 4단계(RLS 적용 전 서버 경계 전환) 작업의 일부로, 주민등록번호
원문 수집을 중단하고 최소 수집 구조로 전환한 내용을 반영한다.

## 1. 수집 항목

| 대상 | 항목 | 비고 |
| --- | --- | --- |
| 간병인(caregivers) | 성명, 휴대폰번호, 주민등록번호 앞 7자리(선택, 마스킹 저장) | 로그인은 Supabase Auth 휴대폰 OTP 세션으로 처리, 별도 비밀번호 없음 |
| 환자(cases) | 성명, 생년월일, 연락처, 성별, 진단명, 입원호실, 보험사, 사고유형, 담당설계사 정보 | 사례(case) 단위로 저장 |
| 위치정보(care_logs) | 간병일지 작성 시점의 위도/경도 또는 미기록 사유 | 작성 시점 1회성 기록, 실시간 위치추적 아님 |
| 사진(care_log_photos) | 간병 증빙 사진 파일 | Supabase Storage `care-log-photos` 버킷 |

## 2. 수집 목적

- 간병인 신원 확인 및 전자간병일지 작성 권한(현재 간병인 여부) 판단
- 보험/사고 관련 사례 정보 확인 및 병원-가족 간 소통
- 간병일지 작성 시 실제 방문 여부에 대한 최소한의 위치 확인(허위 작성 방지)
- 사고유형/진단명 등은 보험 심사·정산 등 업무상 필요에 따른 수집

## 3. 주민등록번호 처리 — 변경된 정책

**이전**: `case-register`, `case-join` 모두 주민등록번호 전체를 평문으로
입력받아 `caregivers.resident_number`에 그대로 저장했다.

**현재(4단계 이후)**:
- 신규 등록/참여 화면은 "주민등록번호 앞 7자리(선택)"만 입력받는다.
- 서버(`lib/resident-number.ts`)에서 `900101-1******` 형태로 마스킹한 뒤
  `caregivers.resident_number_masked`에만 저장한다.
- `caregivers.resident_number`(원문 컬럼)에는 신규 코드에서 어떤 값도
  쓰지 않는다(`app/api/cases/register`, `app/api/cases/join` 모두 확인됨).
- 이 필드는 필수 입력이 아니다(업무상 꼭 필요하지 않다면 비워둘 수 있음).

**전체 주민등록번호 원문이 꼭 필요한 업무가 실제로 있다면**, 평문 저장이
아니라 아래 중 하나로 처리해야 한다(이번 단계에서는 구현하지 않음):
- 애플리케이션 레벨 암호화(예: KMS로 관리되는 키로 AES-GCM 암호화 후 저장,
  복호화는 별도 감사 로그가 남는 관리자 전용 서버 함수에서만 수행)
- 외부 신원확인 서비스 연동(자체 저장을 아예 하지 않는 방식)

## 4. 기존 평문 데이터 처리 계획 (운영 승인 필요, 자동 실행 안 함)

기존에 이미 저장된 `caregivers.resident_number` 평문 데이터는 이번
작업에서 자동으로 삭제하거나 변환하지 않는다. 아래 절차를 별도 운영
승인 후 진행할 것을 권장한다.

1. **백업**: 마이그레이션 전 `caregivers` 테이블 스냅샷을 별도 보관한다.
2. **마스킹 백필**: 기존 `resident_number` 값에서 앞 7자리만 추출해
   `resident_number_masked`를 채우는 스크립트를 애플리케이션 레벨에서
   실행한다(SQL 마이그레이션 파일에 원문을 다루는 로직을 넣지 않는다 —
   SQL 히스토리/로그에 원문이 남는 것을 피하기 위함. Supabase SQL Editor
   실행 이력에도 남을 수 있으므로, 가능하면 서버 스크립트를 1회성으로
   실행하고 즉시 폐기하는 방식을 권장).
3. **원문 컬럼 정리**: 백필과 신규 코드 전환이 끝나고 일정 기간(예: 1
   릴리스 주기) 문제가 없음을 확인한 뒤, `resident_number` 컬럼을 drop
   하거나 접근을 완전히 차단한다. 이 시점부터 RLS 정책에서도
   `resident_number` 컬럼을 아예 노출하지 않는다(`supabase/migrations/
   20260803120500_rls_policies.sql`에 이미 반영됨 — authenticated/anon
   모두 이 컬럼에 대한 select 권한이 없음).
4. **승인**: 위 2, 3단계는 실제 데이터 삭제/변경을 수반하므로 운영
   책임자의 서면 승인 후 진행한다.

## 5. 저장 기간

- 사례(case)는 "간병종료" 상태가 된 뒤에도 즉시 삭제하지 않는다(보험
  심사/분쟁 대응 등 업무상 보관 필요 가능성).
- 구체적인 보관 기간(예: 종료 후 N년)은 법무/보험 업무 담당자와 별도
  협의가 필요하다 — 이번 단계에서는 기술적 삭제 정책을 구현하지 않았다.

## 6. 관리자 접근 기록 필요성

현재 관리자가 `/admin/cases/[id]/print`에서 환자 PDF를 열람/출력할 때
**누가 언제 어떤 사례를 조회했는지 기록하는 로그가 없다.** 개인정보(진단명,
보험정보, 주민등록번호 앞자리 등)에 대한 관리자 접근인 만큼, 향후
`admin_access_log` 같은 테이블에 `(admin_user_id, case_id, action,
accessed_at)`을 기록하는 기능을 추가하는 것을 권장한다(이번 단계 범위
밖, 후속 과제로 남긴다).

## 7. 로그에 개인정보를 남기지 않는 규칙

- `console.log`/`console.error`에 요청 body 전체, 주민등록번호(원문/마스킹
  모두), 환자 성명 등 개인정보를 그대로 출력하지 않는다.
- 서버 라우트에서 에러를 기록할 때는 `error.message`(Supabase/Postgres
  에러 메시지)만 남기고, 그 에러가 발생한 요청의 payload를 함께 로깅하지
  않는다. 이번 단계에서 작성한 `app/api/cases/register`,
  `app/api/cases/join`, `app/api/admin/hospitals/**`,
  `app/api/google-form-sync`는 모두 이 규칙을 따른다.
- 클라이언트 쪽 `setMessage(...)` 문구에도 서버 에러 메시지를 그대로
  노출하지 않고, 미리 정의한 한국어 안내 문구로 변환해서 보여준다(이미
  적용됨).
- Vercel 등 배포 환경의 로그 보존 기간/접근 권한도 이 규칙과 함께
  검토할 것(코드 범위 밖).
