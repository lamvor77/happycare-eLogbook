# 개인정보 처리 정책

해피간병 전자간병일지 시스템이 수집·저장하는 개인정보와 그 처리 원칙을
정리한다. 4단계(RLS 적용 전 서버 경계 전환)에서 주민등록번호 원문 수집을
중단하고 최소 수집 구조로 전환했고, 이번 단계에서 "간병인 주민등록번호
전체 13자리가 실무상 필요하다"는 요구에 맞춰 **평문 저장 대신 서버 측
암호화 저장**으로 다시 전환했다(아래 3절).

**이 문서에서 "운영 확인 필요"로 표시한 항목은 기술적으로 구현되지 않았고,
법무/운영 책임자의 별도 결정이 필요하다는 뜻이다. 코드가 이 항목들을
대신 결정하지 않는다.**

## 1. 수집 항목

| 대상 | 항목 | 비고 |
| --- | --- | --- |
| 간병인(caregivers) | 성명, 휴대폰번호, **주민등록번호 전체 13자리(암호화 저장, 3절)** | 로그인은 Solapi SMS OTP + 자체 장기 세션(HttpOnly 쿠키)으로 처리, 별도 비밀번호 없음(`docs/solapi-caregiver-auth.md`) |
| 환자(cases) | 성명, **생년월일(6자리 YYMMDD + 세기 선택, 서버에서 날짜로 변환, 4절)**, 연락처, 성별, 진단명, 입원호실, 보험사, 사고유형, 담당설계사 정보 | 사례(case) 단위로 저장. 환자는 주민등록번호를 수집하지 않는다 |
| 동의 기록(case_consents) | 등록 동의 6개 항목(boolean) + 동의 문구 버전 + 동의 시각 | IP/User-Agent는 저장하지 않는다(최소 수집 원칙, 운영 확인 필요 — 8절) |
| 위치정보(care_logs) | 간병일지 작성 시점의 위도/경도 또는 미기록 사유 | 작성 시점 1회성 기록, 실시간 위치추적 아님 |
| 사진(care_log_photos) | 간병 증빙 사진 파일(스키마만 존재, 현재 업로드 코드 경로 없음) | Supabase Storage `care-log-photos` 버킷(`docs/data-model.md` 3.6절) |

## 2. 수집 목적

- 간병인 신원 확인 및 전자간병일지 작성 권한(현재 간병인 여부) 판단
- 보험/사고 관련 사례 정보 확인 및 병원-가족 간 소통
- 간병일지 작성 시 실제 방문 여부에 대한 최소한의 위치 확인(허위 작성 방지)
- 사고유형/진단명 등은 보험 심사·정산 등 업무상 필요에 따른 수집

### 간병인 전체 주민등록번호가 필요한 업무 사유

가족간병인 등록은 실제 병원/보험 업무상 간병인 본인 신원을 명확히 확인해야
하는 절차이며, 담당 업무 부서에서 주민등록번호 전체 13자리로 신원을
대조해야 하는 경우가 있다고 확인되었다(요청 근거). 6자리(생년월일)만으로는
동명이인·중복 확인이 불충분하다는 것이 이 요구의 실무적 배경이다.
**이 수집의 구체적 법적 근거(개인정보보호법상 고유식별정보 처리 요건 충족
여부 등)는 이 문서가 아니라 운영/법무 책임자가 별도로 확인해야 한다 —
9절 참고.**

## 3. 간병인 주민등록번호 처리(암호화 저장)

**변경 이력**:
- 4단계: 원문 수집을 중단하고 "앞 7자리만 입력받아 마스킹 저장"으로 전환.
- 이번 단계: 실무상 전체 13자리가 필요하다는 요구에 따라, **평문으로
  되돌리지 않고** 애플리케이션 서버에서 AES-256-GCM으로 암호화한 뒤
  저장하는 방식으로 전환(QR 최초 등록 화면 `app/case-register`부터 적용,
  `app/case-join` 가족간병인 추가는 이번 범위 밖 — 여전히 앞 7자리 방식).

**현재 저장 구조**(`caregivers` 테이블, `supabase/migrations/
20260806090000_encrypt_caregiver_resident_number.sql`):

| 컬럼 | 내용 |
| --- | --- |
| `resident_number_ciphertext` | AES-256-GCM 암호문(base64) |
| `resident_number_iv` | 매 암호화마다 새로 생성되는 랜덤 IV(96비트, base64) |
| `resident_number_auth_tag` | GCM 인증 태그(base64) — 변조 여부 검증용 |
| `resident_number_key_version` | 암호화에 쓰인 키 버전(향후 키 회전 대비) |
| `resident_number_masked` | 표시용 마스킹 값(`900101-1******`), 4단계부터 이미 존재하던 컬럼 재사용 |
| `resident_number`(레거시) | **더 이상 어떤 신규 코드도 쓰지 않는다.** 과거 평문 데이터가 남아있을 수 있음(8절) |

**처리 흐름**(`app/api/cases/register/route.ts`, `lib/
caregiver-resident-number.ts`):
1. 클라이언트가 하이픈 포함/미포함 13자리를 서버로 전송(HTTPS로만 전송,
   `type="text" inputMode="numeric" autoComplete="off"`, 브라우저
   localStorage/sessionStorage에 저장하지 않음).
2. 서버가 숫자만 추출해 13자리인지 검증(`normalizeResidentNumber`).
3. 서버가 즉시 AES-256-GCM으로 암호화(`encryptResidentNumber`)하고,
   마스킹 값을 별도로 계산(`maskResidentNumber`) — 이 시점 이후 원문 변수는
   더 이상 참조하지 않는다.
4. 암호문/IV/인증태그/키버전/마스킹값만 `register_case_v3` RPC 파라미터로
   전달한다(원문은 RPC로도 전달되지 않음 — Postgres 함수 로그/오류
   메시지에도 원문이 남지 않도록 하기 위함).
5. API 응답에는 주민등록번호 관련 값을 어떤 형태로도 포함하지 않는다.

**암호화 키 관리**: `CAREGIVER_RRN_ENCRYPTION_KEY`(서버 전용 환경변수,
`.env.example` 참고). `CAREGIVER_SESSION_SECRET`과 별도의 키를 쓴다. 키
자체는 어떤 문서/커밋/로그에도 값으로 남기지 않는다.

**복호화**: `lib/caregiver-resident-number.ts`에 `decryptResidentNumber()`가
존재하지만, **이번 단계에서는 어떤 API 라우트도 이 함수를 호출하지
않는다.** 원문 조회가 실제로 필요해지면 5절의 조건을 갖춘 별도 기능으로
분리한다.

## 4. 환자 생년월일 처리

환자는 주민등록번호를 수집하지 않는다. 생년월일은 "6자리(YYMMDD)"만
입력받고, 화면 문구도 "주민등록번호"가 아니라 "생년월일 6자리"로 표시한다.
6자리만으로는 세기(1900년대/2000년대)를 알 수 없으므로, 화면에서 별도로
세기를 선택받아 서버(`lib/registration-validation.ts`의
`normalizePatientBirthDateParts`)가 `cases.patient_birth_date`(date 타입)로
변환한다 — 세기를 임의로 추정하는 로직은 없다(추정이 틀리면 잘못된 생년이
영구히 저장되는 위험이 있어 의도적으로 배제).

## 5. 마스킹 표시 정책(관리자 화면)

- 관리자 화면(사례 상세, 사례 목록, PDF 출력)은 간병인 주민등록번호를
  **표시하지 않는다.** 현재 어떤 관리자 화면도 `resident_number`/
  `resident_number_masked`를 조회·표시하지 않음을 코드로 확인했다(작업
  H, 10절의 보안 검색 결과 참고).
- 향후 마스킹 값이라도 표시가 필요해지면 "앞 6자리(생년월일) + 성별 식별
  1자리"까지만 노출하고 나머지는 마스킹하는 기존 형식(`900101-1******`)을
  그대로 따른다. 전체 번호 자동 노출은 금지한다.
- 업무상 원문 조회가 꼭 필요한 경우, 이번 단계에서 화면에 바로 붙이지
  않는다. 아래 조건을 모두 갖춘 별도 후속 기능으로 분리해야 한다:
  - 관리자 재인증(비밀번호 재입력 등)
  - 조회 사유 입력
  - 조회 자체에 대한 감사 로그(누가, 언제, 어떤 caregiver의 정보를,
    무슨 사유로 조회했는지)
  - 짧은 시간만 표시(예: 화면 이탈/타임아웃 시 자동 마스킹 복귀)

## 6. 접근 권한

- `resident_number_ciphertext`/`iv`/`auth_tag`/`key_version` 4개 컬럼은
  Supabase RLS 컬럼 단위 GRANT에 **포함되어 있지 않다** — `authenticated`/
  `anon` 역할은 이 컬럼들을 select할 권한 자체가 없다(GRANT를 추가하지
  않는 것 자체가 보호 조치, `20260806090000_encrypt_caregiver_resident_number.sql`
  참고). 오직 `service_role`(`lib/supabase-admin.ts`, 서버 전용 파일)만
  접근 가능하다.
- `resident_number`(레거시 원문 컬럼)도 이미 4단계부터 동일하게
  select 권한이 없다.
- 암호화 키(`CAREGIVER_RRN_ENCRYPTION_KEY`)는 Vercel 등 배포 환경의 서버
  전용 환경변수로만 존재하며, 이 키에 접근할 수 있는 사람 범위(배포
  환경변수 접근 권한)를 운영팀이 별도로 관리해야 한다.

## 7. 보유 기간 — 운영 확인 필요

- 사례(case)는 "간병종료" 상태가 된 뒤에도 즉시 삭제하지 않는다(보험
  심사/분쟁 대응 등 업무상 보관 필요 가능성).
- 간병인 주민등록번호(암호화된 형태 포함)를 얼마나 보관할지, 간병
  종료/간병인 연결 해제 후 언제 파기할지에 대한 **구체적 보유 기간은
  정해져 있지 않다.** 법무/보험 업무 담당자와 별도 협의가 필요하다 —
  이번 단계에서는 기술적 보유기간 정책(자동 만료/파기 배치 등)을
  구현하지 않았다.

## 8. 파기 절차

- **암호화 컬럼**: 보유 기간이 확정되면(7절), 해당 caregiver의
  `resident_number_ciphertext`/`iv`/`auth_tag`/`key_version`/
  `resident_number_masked`를 null 처리하는 절차를 별도로 마련해야 한다
  (자동화 배치는 이번 단계에서 구현하지 않음).
- **레거시 평문 컬럼(`resident_number`)**: 기존에 이미 저장된 평문
  데이터는 `supabase/migrations/manual/cleanup_resident_number.sql`
  (마스킹 백필 → 원문 null 처리 → 컬럼 drop 검토) 절차를 그대로 따른다.
  이번 단계에서 추가된 `supabase/migrations/manual/
  migrate_caregiver_resident_number_to_encrypted.sql`은 "평문 →
  암호화 컬럼" 이행 절차만 다루고, 원문 정리는 여전히
  `cleanup_resident_number.sql`의 2~4단계를 따른다.
- 두 파일 모두 SQL 자동 실행 대상이 아니며, 값 자체를 SELECT로 출력하지
  않고, 데이터 삭제/변경을 수반하는 단계는 운영 책임자의 서면 승인 후에만
  진행한다.

## 9. 기존 평문 데이터 이행 계획(운영 승인 필요, 자동 실행 안 함)

기존에 이미 저장된 `caregivers.resident_number` 평문 데이터는 이번
작업에서 자동으로 삭제·암호화하지 않는다. 권장 절차:

1. **백업**: 이행 전 `caregivers` 테이블 스냅샷을 별도 보관한다.
2. **암호화 백필**: `supabase/migrations/manual/
   migrate_caregiver_resident_number_to_encrypted.sql`의 절차대로,
   SQL이 아니라 1회성 서버 스크립트로 `lib/caregiver-resident-number.ts`의
   `normalizeResidentNumber()`/`encryptResidentNumber()`/
   `maskResidentNumber()`를 재사용해 암호화 컬럼을 채운다(스크립트는
   실행 후 즉시 폐기, 원문/암호문/키를 로그에 남기지 않는다).
3. **원문 컬럼 정리**: 백필 검증이 100% 일치하고 일정 기간(예: 1릴리스
   주기) 문제가 없음을 확인한 뒤, `cleanup_resident_number.sql`의
   원문 null 처리 → 컬럼 drop 단계로 진행한다.
4. **승인**: 2, 3단계는 실제 데이터 변경/삭제를 수반하므로 운영 책임자의
   서면 승인 후 진행한다.

## 10. 법적 근거 — 운영 확인 필요

주민등록번호는 개인정보보호법상 고유식별정보로, 원칙적으로 법령에 별도
근거가 있거나 정보주체의 별도 동의를 받은 경우 등 제한된 요건에서만
처리할 수 있다. 이 문서와 코드는 다음을 **구현했을 뿐** 법적 요건 충족
여부를 판단하지 않는다:
- 암호화 저장, 접근 통제, 마스킹 표시, 로그 미노출(3, 5~8절)
- 등록 동의 화면의 개인정보 수집·이용 동의 항목(`case_consents.
  privacy_consent_confirmed`)

**아래는 운영/법무 책임자가 별도로 확인·문서화해야 한다(코드로 대체할 수
없음):**
- 간병인 주민등록번호 전체 13자리 수집이 개인정보보호법 제24조(고유식별
  정보 처리 제한) 등 관련 법령의 요건을 충족하는지
- 별도 동의(주민등록번호 처리에 대한 별도 동의)가 필요한지, 필요하다면
  현재 `case_consents`의 동의 문구가 이를 충분히 포괄하는지
- 7절의 보유기간, 8절의 파기 절차가 실제 법적 기준을 충족하는지

## 11. 관리자 접근 기록 필요성

현재 관리자가 `/admin/cases/[id]/print`에서 환자 PDF를 열람/출력할 때
**누가 언제 어떤 사례를 조회했는지 기록하는 로그가 없다.** 개인정보(진단명,
보험정보 등)에 대한 관리자 접근인 만큼, 향후 `admin_access_log` 같은
테이블에 `(admin_user_id, case_id, action, accessed_at)`을 기록하는 기능을
추가하는 것을 권장한다(이번 단계 범위 밖, 후속 과제로 남긴다).

## 12. 로그에 개인정보를 남기지 않는 규칙

- `console.log`/`console.error`에 요청 body 전체, 주민등록번호(원문/
  마스킹/암호문/IV/인증태그 모두), 환자 성명 등 개인정보를 그대로
  출력하지 않는다. `app/api/cases/register/route.ts`는 요청 본문을 통째로
  로그로 남기지 않고, 오류 발생 시에도 `error.message`만 남긴다.
- 서버 라우트에서 에러를 기록할 때는 Supabase/Postgres 에러 메시지만
  남기고, 그 에러가 발생한 요청의 payload를 함께 로깅하지 않는다.
- 클라이언트 쪽 `setMessage(...)` 문구에도 서버 에러 메시지를 그대로
  노출하지 않고, 미리 정의한 한국어 안내 문구로 변환해서 보여준다.
- 주민등록번호 입력값은 브라우저 콘솔에 출력하지 않고, localStorage/
  sessionStorage 등 어떤 브라우저 저장소에도 저장하지 않는다(React
  state에만 보관, 제출/오류 후 적절한 시점에 초기화).
- Vercel 등 배포 환경의 로그 보존 기간/접근 권한도 이 규칙과 함께
  검토할 것(코드 범위 밖).
